# BetaBuddy Android：导航、岩馆容器、攀爬册与语言

Android 版和 iOS 版是同一个产品：同样的两个入口、同样的五种语言、同样的本地与诚实性原则。产品定位见 [../ios/product-design.md](../ios/product-design.md)，岩馆功能和数据包接口见 [../ios/gym-design.md](../ios/gym-design.md)。这里只写 Android 上怎么落地，以及和 iOS 不一样的地方；接口约定不重复抄。

## 导航

单 Activity（`MainActivity`），Compose 界面，`navigation-compose` 管页面栈。

```
home ─┬─ 岩馆（标签 0，启动落点）
      ├─ 攀爬册（标签 1，JournalScreen 内部自己切 列表 → 导入 → 回看）
      └─ 齿轮 ──▶ settings（设置与关于）─┬─ settings/privacy（隐私政策）
                                        └─ settings/licenses（开源许可）
```

- **底部两个入口**在 `home` 这一页里，不是 NavHost 的路由。岩馆始终留在界面树里，攀爬册盖在它上面；这样切到攀爬册再回来，岩馆页面不重载。攀爬册的界面状态用 `SaveableStateProvider` 保存，它的 ViewModel 挂在 `home` 这一层，切标签不会丢。
- **底部导航**和 iOS 一样：两个入口等宽，最右边是一个齿轮，打开「设置与关于」。齿轮在两个入口下都在，包括岩馆的 3D 页面铺满的时候（页面顶部归数据包，原生不在上面叠按钮）。
- **设置与关于**是一页，结构与 iOS 的 `AboutView` 相同：第一项是语言（「跟随系统」加五种语言，各用自己的文字写），然后是本地说明、分析边界、岩馆说明、记录管理、隐私政策、开源许可、帮助与支持、版本。进入它的地方有四处：底部的齿轮；攀爬册首页右上角的圆形按钮（`JournalScreen(onOpenSettings)`）；岩馆说明页和无数据包页右上角的同一个按钮；数据包页面自己发来的 `openSettings` 消息。
- **返回**：系统返回手势先退设置页，再让攀爬册内部回到列表，再从攀爬册回到岩馆，最后离开应用。Manifest 开了 `enableOnBackInvokedCallback`，页面之间有预测性返回动画。
- **边到边**：`enableEdgeToEdge()`，状态栏和导航栏透明、深色图标，底下是纸白。原生页面用 `PaperPage` 避开状态栏和刘海；底部标签栏自己垫上导航栏/手势条的高度。标签栏以上的内容区已经扣掉了标签栏占掉的底部 inset，里面的页面再用 `imePadding()` 时不会多垫一截。
- **方向**：Manifest 写了竖屏。大屏设备上系统会忽略这个限制，布局按可用宽度排，不依赖固定方向。
- **只有浅色**，和 iOS 一致。

## 视觉

`ui/theme/Theme.kt` 的 `BB` 与 iOS `DesignSystem.swift` 同值：纸白 `#F5F2E8`、墨黑 `#1A1F1A`、荧光黄绿 `#D1F24A`、淡紫 `#D1CCF0`、次要文字 `#616659`、分隔线为墨黑 13%。标题用系统字体的最粗字重，圆角 14–26。Material 3 只是底座（颜色表映射到 `BB`），界面用 `ui/common` 里自己的组件：`PaperPage`、`Stamp`、`BigButton`、`SectionLabel`、`Stat`、`ColorCard`、`CircleIconButton`、`BBIcons`（自绘线条图标和品牌标记，不带图标字体）。岩馆、攀爬册和设置用的是同一套；攀爬册独有的几个小件（描边按钮、进度条、播放控制）在 `journal/JournalStyle.kt`，颜色和字体仍取自 `BB`。

英文小标（`GYM / UNOFFICIAL`、`KEEP IT HONEST` 等）是品牌标记，不翻译。

## 岩馆容器

对应 iOS 的 `GymPack.swift` / `GymView.swift`，代码在 `gym/`：

| 文件 | 内容 |
| --- | --- |
| `GymManifest.kt` | 读 `manifest.json`（字段与宽容写法同 iOS；`venues[].directoryIds` 用来对上目录里的岩馆） |
| `GymPack.kt` | 数据包状态（无 / 不完整 / 就绪）、路径安全检查、入口 URL、内容类型表 |
| `GymMessage.kt` | 页面 → 应用的消息、应用 → 页面的调用、垫片脚本 |
| `PackWebView.kt` | 显示数据包里一个页面的 `WebView`：创建、离线拦截、只提供清单里的文件、消息垫片。岩馆页面和攀爬册的分析页面共用 |
| `GymSession.kt` | 岩馆那一个页面：加载、状态、消息处理、生命周期 |
| `GymScreen.kt` | 说明页、空状态、加载中、失败、页面本身 |

前三个文件不依赖 Android 类型，单元测试直接在 JVM 上跑。

### 数据包在哪

`app/src/main/assets/gympack/`，被 Git 忽略，由 `android/scripts/install-gym-pack.sh` 校验后拷入。启动时读清单、确认格式版本、确认清单里每个文件都能打开；不重算摘要（安装脚本算过，APK 之后有签名）。没有数据包不是错误：入口保留，显示「这个构建没有内置岩馆数据」。

### 加载方式

页面的地址是 `https://appassets.androidplatform.net/gympack/<entry>`。这个域名是 `WebViewAssetLoader` 的保留域名，从不解析，请求在应用里就地回答：

- 只回答 `/gympack/` 之下、**清单里列出的**路径（比 iOS 更严：目录里多出来的文件也不提供）。其余本地域名请求回 404。
- 响应头和 iOS 一样带 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff` 和同一条内容安全策略（去掉了 `gympack:` 协议名）。内容类型按同一张扩展名表给出。
- 这是普通的 https 同源环境，`<script src>`、`fetch`、ES module、Blob Worker 都按常规工作。

入口 URL 的查询参数与 iOS 一致：`hint=0`、`lang=<代码>`，Debug 构建的附加查询串排在后面。

### 离线保证

四层，任何一层单独都够用：

1. **没有 `INTERNET` 权限。** Manifest 不声明，并用 `tools:node="remove"` 去掉依赖库合并进来的声明。没有这个权限，系统不给进程任何网络套接字，WebView 也一样。这一层由系统强制，不依赖应用代码。
2. `WebSettings.blockNetworkLoads = true`。
3. `shouldInterceptRequest` 里除了数据包地址和内存里的 `data:` / `blob:` / `about:` 之外，一律回空的 403；`shouldOverrideUrlLoading` 拦掉数据包之外的导航。
4. 响应头里的内容安全策略不允许任何远程源。

另外关闭了文件访问、内容访问、混合内容、定位、弹窗、缩放，关掉了 Safe Browsing 和 WebView 的指标上报（Manifest 里的两条 `meta-data`）。页面存储在每次启动后第一次打开数据包页面之前清空。这些规则都在 `PackWebView` 里，数据包的两个页面（岩馆、分析）用的是同一份。

姿态识别用的 MediaPipe Tasks 依赖 Google 的 datatransport 库（它自己的使用统计上报）。除了没有联网权限之外，Manifest 还去掉了这个库用来发现上报后端的服务：没有后端，每条事件在入库和排程之前就被丢弃。

### 消息桥

页面是给 iOS 写的，只会调用 `window.webkit.messageHandlers.gym.postMessage(对象)`。Android 上：

- `addJavascriptInterface` 注入一个对象 `BetaBuddyGymNative`，只有一个方法 `postMessage(字符串)`。
- 一小段垫片脚本在文档开始时运行（`WebViewCompat.addDocumentStartJavaScript`，只对数据包的源生效），把 `window.webkit.messageHandlers.gym.postMessage(obj)` 接到 `BetaBuddyGymNative.postMessage(JSON.stringify(obj))`。WebView 太旧不支持文档开始脚本时（例如 Android 12 模拟器上的 WebView 91），本地地址提供 HTML 时把垫片写进文档、作为第一个脚本，另外在 `onPageStarted` / `onPageFinished` 再注入一次，页面的第一条消息不会因为抢先后而丢。
- 垫片只在主框架里生效。消息在主线程解析，类型和处理与 iOS 相同：`ready` 收起加载状态；`hintSeen` 记在本机，之后的入口 URL 带 `hint=0`；`routeSelected` 只留 id 和名称，只在内存里；`openSettings` 打开原生的「设置与关于」（只在岩馆页面在前台时响应）；`error` 在 `ready` 之前才盖失败页，之后的只写日志。不认识的类型和多出来的字段忽略。

应用 → 页面仍是 `window.BetaBuddyGym.openWall(id)` / `openRoute(id)`，用 `evaluateJavascript` 调用，参数经 JSON 字符串编码。

### 生命周期

- `WebView` 归 `GymSession` 所有，`GymSession` 放在 Activity 级的 `GymViewModel` 里。切标签、进设置、屏幕配置变化（包括切换语言引起的 Activity 重建）都不销毁它；`WebView` 用 `MutableContextWrapper` 创建，重建后换到新的 Activity 上，不持有旧的。
- 岩馆不在前台（切到攀爬册、应用退到后台）时调用 `WebView.onPause()` 并把视图设为不可见，回来时恢复。
- **切换语言**：页面的语言由 URL 决定，所以语言变了就带新的 `lang` 重新加载，并在页面 `ready` 后对之前选中的线路调用 `openRoute`。
- **渲染进程被回收**（`onRenderProcessGone`）：丢掉这个 `WebView`，显示「岩馆页面被系统回收了」和「重新加载」，应用不崩溃；重新加载时新建一个。
- 页面首次加载完成前盖着纸白底的「正在打开岩馆…」，避免白屏闪烁。

### 安全区

iOS 上页面延伸到状态栏下面，用 `env(safe-area-inset-*)` 自己留白。Android WebView 对安全区的支持随版本不一，所以 Android 上反过来：原生侧把 `WebView` 放在状态栏和刘海**之内**（上方和两侧按系统 inset 留出，露出的是和页面顶部同色的纸白），并且不把 inset 传给 `WebView`，页面拿到的 `env(safe-area-inset-*)` 恒为 0。底部是原生标签栏，标签栏自己垫导航栏的高度，页面的底部抽屉不会被遮住。

### 调试启动参数

只在 Debug 构建里生效，用 `adb shell am start` 的 extra 传入：

| extra | 类型 | 作用 |
| --- | --- | --- |
| `initialTab` | `--ei` 0 / 1 | 启动落在岩馆 / 攀爬册 |
| `gymNoticeSeen` | `--ez true` | 跳过进入前的说明页（会记住） |
| `gymQuery` | `--es` | 原样接到入口 URL 的查询串后面 |
| `gymOpenWall` / `gymOpenRoute` | `--es` | 页面 `ready` 后调用对应接口 |

Debug 构建还可以用 Chrome 的 `chrome://inspect` 连上页面。加载耗时和页面报告的错误写入 logcat（标签 `gym`），不离开设备。

## 语言

- 资源目录：`values/` 是英语（所以不支持的系统语言读到英语），`values-b+zh+Hans`、`values-b+zh+Hant`、`values-ja`、`values-ko`。壳、岩馆、设置的文字在 `strings.xml`，文件夹与筛选在 `strings_album.xml`，攀爬册在 `strings_journal.xml`，应用内相机在 `strings_capture.xml`。译文取自 iOS 的 `Localizable.xcstrings`，提到平台的地方（iPhone、相册应用）改成对 Android 成立的说法。
- `res/xml/locales_config.xml` 列出五种语言并在 Manifest 里登记，Android 13+ 的系统设置里会出现「应用语言」。
- **应用内语言设置**（「设置与关于」的第一项）：「跟随系统」加五种语言，各用自己的语言写。用 AppCompat 的按应用语言接口 `AppCompatDelegate.setApplicationLocales`：Android 13+ 和系统设置是同一个值；更低的版本由 AppCompat 自己保存（Manifest 里 `AppLocalesMetadataHolderService` 的 `autoStoreLocales`）。「跟随系统」就是清空应用语言。选了之后 Activity 立即以新语言重建，仍停在「设置与关于」；回到岩馆时页面带着新的 `lang` 重新加载并回到原来的线路。
- `AppLanguage.current(context)` 返回 `zh-Hans` / `zh-Hant` / `en` / `ja` / `ko` 之一。做法是每个 `strings.xml` 里放一条自己的语言代码（`app_language_code`），读到的就是界面实际在用的那套资源，回落到英语时也对。它用于入口 URL 的 `lang=` 和清单里的 `gymNameLocalized`。
- **隐私政策**随应用内置，离线显示：`res/raw*/privacy_policy.txt` 有简体中文、繁体中文、英语三份，日语和韩语界面读英语。文字在 iOS 版的基础上改成了对 Android 成立的说法（没有申请联网权限、系统照片选择器、平台自带的定位、卸载即删除）。

## 攀爬册

对应 iOS 的 `JournalView` / `ImportView` / `ReviewView` / `CaptureView` 和 `Core/` 里的存储与分析，功能与文字一致。入口只有 `JournalScreen(onOpenSettings)`，列表 → 导入 → 回看在它内部切换，不占用 NavHost 的路由；拍摄界面和分析页面是盖住整个界面的全屏对话框。`JournalViewModel` 挂在 `home` 这一层。

| 目录 | 内容 |
| --- | --- |
| `data/` | 记录的数据结构（kotlinx-serialization）、攀爬方式与难度体系（`Discipline`、`GradeScale`）和 `ClimbStore`：`filesDir/BetaBuddy/` 下的 `archive.json`、原片、缩略图、分析页面交回的结果和剪辑计划、拍摄计划，原子写入；索引读不出来时原样保留、不覆盖。`CaptureSweep` 在启动时清理 `staging/` |
| `pose/` | `VideoAnalyzer`（解码与推理）、采样与导入限制 |
| `journal/` | 列表、文件夹与组合筛选、导入流程、岩馆目录与距离、姿态识别服务（`AnalysisService`）、相机开关（`CameraGate`）、文字与格式化 |
| `review/` | 回看：播放、完攀开关、分享；数据包分析页面的宿主（`AnalysisBridge`、`AnalysisFrames`、`AnalysisSession`、`AnalysisScreen`）；拍过的记录的分析队列（`AnalysisQueue`） |
| `edit/` | 自动剪辑，见下面的[自动剪辑](#自动剪辑)：读剪辑计划（`EditPlan`）、时间与镜头窗口的换算（`EditTimeline`）、谁能被消掉（`Passers`）、找人（`PeopleFinder`）、渲染（`EditRenderer`、`EditEffect`）、剪辑页面（`EditScreen`）、缓存里的文件与分享（`EditFiles`） |
| `capture/` | 应用内相机，见下面的[拍一趟](#拍一趟) |

- **选视频**用系统照片选择器（`PickVisualMedia`，只选视频），不需要任何存储权限；选中的那一段被复制到应用私有目录的 `staging/`，超过 500 MB 在复制途中就停下。
- **分析**：`MediaExtractor` + `MediaCodec` 顺序解码，不采样的帧在颜色转换之前丢弃；采样帧按旋转信息摆正、缩放后交给 MediaPipe Pose Landmarker Full（视频模式，CPU，33 点），与 iOS 是同一个模型文件，加载前核对 SHA-256。同一时间只跑一个分析，在专用线程上；取消和设备过热在帧与帧之间检查。默认只保存视频和缩略图，不运行模型；姿态识别只在点「分析这一趟」时（或拍过的记录进分析队列时）运行，是分析页面的第一步，回看页不单独提供。分析由 `AnalysisService` 持有，离开页面、切换入口或退到桌面不取消。请求先写入存档，任务按队列串行执行；服务被系统结束时保留请求，下次打开应用重试；显式停止清除请求。结果只替换分析字段，保留同期编辑的笔记、日期与难度。Android 15+ 使用 `mediaProcessing` 前台服务，较旧系统使用 `dataSync` 的本地文件处理类型。Android 13+ 在用户要分析时询问通知权限（可选），用来在通知栏显示进度，拒绝不影响分析；分析不需要屏幕常亮。
- **回看**：Media3 ExoPlayer 画到 `TextureView`，画面按原比例放在黑底里；0.1 秒步进按精确定位，0.5× 慢放，时间、三个按钮和速度在一行。不叠骨架，不写笔记（旧记录里的笔记照常存着、照常进分享文字），完攀开关改了就存。页面上的说明只留分析按钮下一句「自动识别，可能认错」。播放器等 `TextureView` 有了 surface 才开始解码，这样暂停状态下打开也能看到第一帧。原生不计算、不显示评分或指标；分析在数据包的分析页面里。
- **诚实性**与 iOS 同一套规则：识别出的姿态不跨检测空白延续；原生文字不给评分、不说“精准”“最佳”一类的话，`JournalStringsTest` 检查文字里没有这些词。分析页面里的内容由数据包自己负责说明。
- 存档里不写界面语言：存类型或原值，显示时取当前语言的文字。
- **攀爬方式与难度**：记录多了 `discipline`（`boulder` / `toprope` / `lead`，可以没有）和 `disciplineAuto`（这个值是分析页面判断的，不是用户选的）两个字段，旧存档没有它们，照常读。导入页和「整理这一趟」里是一个三段的选择（抱石 / 顶绳 / 先锋），没有说明文字；难度选择器跟着它换体系：抱石 `V0`–`V16`，顶绳和先锋 `5.5`–`5.9`、`5.10a`–`5.14d`，存的就是这些原值。没选攀爬方式的记录按抱石的体系。换到另一种体系时，原来那种体系的难度回到「未标级」。难度始终由用户标，应用和数据包都不推断。分析页面随结果给出攀爬方式的判断时：用户自己没选过就记下来、标成自动的——但自动的判断从不动用户标的难度：记录上已经有另一种体系的难度时，这个判断干脆不存，攀爬方式和难度都保持原样（只有用户自己改攀爬方式才会清掉体系不对的难度）；用户选过的不会被改，并且在开始分析时告诉页面（`meta.discipline`），页面就不再判断。在「整理这一趟」里不碰这个选择、只改别的，自动的仍然算自动的。

### 姿态数据与存档

每个采样帧存 33 个画面关键点（`joints`，归一化坐标与置信度），以及同一帧的 world landmarks（`world`，33 个 `[x, y, z, visibility]`）。新写入的数值保留 4 位小数。`world` 是可选字段：没有它的记录照常读取、照常回看，要用分析页面时先重新识别一次姿态。存档里不认识的字段读到时忽略，下一次写索引时不再带上，记录本身不受影响。字段名与 iOS 相同。

### 分析这一趟

分析（计算和界面）都在场馆数据包的一个页面里，原生只做宿主：准备数据、交给页面、保存页面交回来的结果、响应页面的消息。页面怎么算不在这个仓库里，这里也不描述。接口以已安装数据包里的约定为准。

现在内置的数据包（1.10.0）在接口上比 1.9.8 多了两样：分析结果的消息里可以带两个可选字段，`edit`（剪辑计划）和 `discipline`（攀爬方式的判断），分析不了时的 `analysisError` 也可以带 `discipline` 和 `edit`（`edit` 与结果里的是同一种对象、同一个大小上限；带了就存成这条记录的剪辑计划，没带时不动已经存着的那一份；手持跟拍的绳攀片子常常分析不了，但攀爬方式仍然说得出来；原生照样按自动判断存下，不覆盖用户的选择、不改用户标的难度），开始分析时可以多告诉页面片子的实际时长和用户选的攀爬方式；原生怎么用见上面的「攀爬方式与难度」和下面的「自动剪辑」。页面上显示的内容没有因此多出什么。页面本身（下面这一段是按 1.9.8 写的，1.10.0 的页面这一轮没有在 Android 上打开过）一步一步地看：先描出画面里认出的这条线的点，每一步标出下一个手点和脚点；一个剪纸小人按视频里每一帧认出的姿态走一遍这一趟，认不出来的地方淡出；最后是从这一趟里量出的几条建议，点一下跳到视频里那一刻。模型推演的走法和岩点用法的名称不显示。这些都是数据包的行为，与 iOS 相同，产品口径见 [product-design.md 的「分析诚实性」](../ios/product-design.md#分析诚实性)；原生在入口下面的那行说明写的是同一件事：自动识别、可能认错、不是教练意见。

- **入口**：回看页在视频和播放控制下面。数据包的清单里没有分析页面（或者这个构建根本没有数据包）时不显示，不留空壳。没有保存过结果时是主按钮「分析这一趟」；有结果时是「看分析」，旁边一个次要的「重新分析」（丢掉保存的结果，从头再来）。按钮下面一行说明。
- **先有姿态**：这条记录还没有识别过姿态，或者是没有 world landmarks 的旧存档，点了先走原有的姿态识别队列（同样的后台服务、进度、停止、错误提示），识别完自动进入分析页面。等待期间离开回看页就不再自动进入，姿态识别本身照常跑完。没有数据包的构建里回看页不做姿态识别。
- **分析页面**是盖住整个界面（包括底部导航）的全屏对话框：上面一条原生的窄栏，右边是「完成」，取画面期间左边显示「正在准备画面…」；下面是 `WebView`。它和岩馆页面用同一个 `PackWebView`（同一个本地地址、同样只提供清单里的文件、同样的离线拦截和消息垫片），地址是分析页面加 `lang=<界面语言>`。`WebView` 放在系统栏之内，不把 inset 传给页面。系统返回等于「完成」。
- **页面就绪后**：有保存的结果就原样交回页面显示；没有就开始一次新的分析（开始时告诉页面记录 id、画面大小、片子的实际时长，以及用户自己选过的攀爬方式）——从原片里均匀取约 60 帧（最密每 0.1 秒一帧）、短边 540 像素（竖屏即宽 540，不放大）、方向已转正（与姿态坐标同一方向）的 JPEG，逐帧交给页面，再把存档里的姿态分批（每批 40 帧）交过去，然后让页面开始算。取画面在后台线程用 `MediaMetadataRetriever` 做（API 27 起直接取缩小的帧，API 26 取原尺寸再缩），只在内存里，不落盘。
- **跟踪用的小图**（数据包 1.10.0 起的可选调用 `addTrackFrame(t, jpegBase64)`）：正常的那组画面交完之后、让页面开始算之前，再把整段片子的小图交过去——大约每秒 3 张、短边 270 像素、JPEG 质量 50、最多 900 张（片子再长就拉开间隔），方向和前一组画面一样是转正的。同样在后台线程取、只在内存里、可以取消；后台分析队列走的是同一段代码，所以也会交。每次调用都先看页面有没有这个函数，第一次发现没有（旧数据包）就不再取、不再交；取不出来时一张都不交，分析照常继续。
- **传给页面的字符串**（记录 id、JPEG、姿态、保存的结果）都经 JSON 编码生成 JavaScript 字面量，不手拼引号。
- **页面交回结果**：原样写成 `filesDir/BetaBuddy/<记录 id>.analysis.json`（与原片同一个目录，同样先写临时文件再改名，同样不进备份）；随结果来的剪辑计划存成 `<记录 id>.edit.json`，攀爬方式的判断记进记录（见上面的「攀爬方式与难度」和下面的「自动剪辑」）；同时把页面用的身材参数记在应用私有的 `SharedPreferences`（`journal` 里的 `analysisClimber`），下一次新的分析带上。用户在页面里调整之后页面会再交一次，覆盖保存。删除记录时结果文件一起删。
- **页面要看视频里的某一刻**：关掉分析页面，回看定位到那一秒并暂停，视频区域滚回可见位置。
- **页面说分析不了**：页面自己显示原因；原生不保存结果，分析页面留着让用户看。这条消息里带了攀爬方式的判断或剪辑计划时，两样照常存下（见上）。进度消息不处理（页面自己画进度）。不认识的消息忽略。岩馆页面的消息处理没有变化，两个页面各有各的 `WebView` 和解析。
- **失败**：页面没加载出来、渲染进程被系统回收、原片读不出画面时，盖一张说明卡片；前两种可以「重新加载」。
- 分析页面开着时发生 Activity 重建（例如系统字号、多窗口尺寸变化），页面会重新打开：有保存的结果就直接显示，没有就重新开始。

### 自动剪辑

分析页面随结果交回一份剪辑计划（接口见数据包的约定；计划怎么来的不在这个仓库里，这里也不描述）。原生把它原样存成 `filesDir/BetaBuddy/<记录 id>.edit.json`：每来一次结果就替换，结果里没带计划就删掉上一份，随分析结果和记录一起删；不认识的字段忽略，`v` 不是 1 的计划当作没有。回看页在分析按钮下面多一个「自动剪辑」，只在这条记录存着能用的计划时出现，有没有保存的分析结果都一样（页面分析不了但给了计划的片子，按钮就在「分析这一趟」下面）——旧数据包存下的结果没有计划，要重新分析一次才有。

原生只照计划执行，自己不判断任何攀岩上的事：

- **时间**：输出是计划里的源片段按顺序接起来，每段一个速度（0.2–4 倍），片段可以重复、可以往回（回放）。慢镜头只是把时间戳拉开，不合成新帧；快的片段按原片帧率（最高 60）抽帧。「慢镜头」关掉时只放计划里的 `trim`（这一趟）一段、原速。
- **镜头**：每个源时刻一个窗口（中心和 1–8 倍的放大），相邻关键帧之间用 smoothstep 过渡，两端保持，窗口不出画面；片段自带镜头时用它自己的。计划顶层写着 `"cameraMode": "track"` 时，关键帧（计划的和各片段自带的）是一条已经平滑过的密集轨迹，相邻两帧之间改成按直线走，两端保持和不出画面照旧；没有这个字段或是别的值，就是 smoothstep。「推拉镜头」关掉就是整幅画面。输出与原片同比例，长边最多 1920。
- **消除路人（未开放）**：已经实现，但 `EditOptions.REMOVAL_OFFERED` 关着，剪辑页不显示这个开关，剪辑时也不认人；在带路人的真实视频上验证过之前不打开。打开之后的做法见下一段。
- **剪辑页面**是盖住整个界面的全屏对话框：剪出来的片子循环播放，下面最多三个开关（计划里有对应内容的才出现，默认都开）、「分享视频」和一句「自动剪辑，可能剪错。」，右上角「完成」。改一个开关就重新渲染；找人和做底图只做一次，之后只重新导出。渲染中显示「正在剪辑…」和进度；失败时显示系统给的原因和「再试一次」。
- **文件**：剪出来的 mp4（H.264，没有声音轨）放在应用缓存的 `edits/<记录 id>/` 里，不属于记录：关掉页面就删，删记录时删，进程被结束留下的在下次打开攀爬册时清掉。不写相册，不写外部存储。「分享视频」经应用自己的 `FileProvider`（只能给出这个目录里的文件、按次授予读权限）把这一个文件交给系统分享面板，不需要存储权限；交出去之后由用户选的应用处理。
- **实现**：Media3 Transformer 把每个片段当作一个带裁剪范围和速度的条目排成一列，画面效果是一个自己的 OpenGL 着色器（窗口裁切，加上用底图盖掉路人区域）。着色器从管线拿到的只有每帧的输出时间戳，所以每个片段的着色器把它见到的第一帧当作片段的起点，之后按「过去的输出时间 × 速度」推回源时刻（误差不超过一帧）；这靠的是每个片段各有自己的一个效果对象，管线因此为每个片段重建着色器。帧率上限只加在比原速快的片段上：原速和慢放的片段一帧不丢（Media3 的限帧会把早到零点几毫秒的帧丢掉，普通片子的时间戳常常这样，每个接点后面就会顿一下）。HDR 片子按 SDR 输出。导出不向系统的媒体指标服务登记。

**消除路人（未开放），只在能消干净的时候。** 规则是每个人「要么全程消掉，要么完全不动」：

1. 导出之前先把计划覆盖的那一段过一遍，每隔约 0.12 秒在缩小的画面上找人（随应用打包的 EfficientDet-Lite2，MediaPipe 的 `ObjectDetector`，CPU，只要「人」这一类），把相邻两次找到的同一个人连成一条轨迹；中间漏掉一两次（最多 1 秒）用前后的位置补上。
2. 一条轨迹要同时满足下面几条才会被消掉，有一条在任何一刻不满足，这个人就全程原样留着：
   - 他的区域（检测框放大一圈）在会被换掉的整段时间里都不碰计划里的 `keep` 框（也放大一圈）——包括两次找到之间补出来的位置，和首尾各多留的 0.3 秒；碰到过攀爬者的人不动，哪怕只有一瞬间；
   - 轨迹是完整的：从这一段的开头或画面边缘开始，到这一段的结尾或画面边缘结束——在画面中间跟丢的人不消，免得他凭空出现或消失；
   - 底图在他经过的每一处都有像素；
   - 在每一次找到他的那一帧，他周围一圈的画面和底图对得上（差得多说明灯光变了、机位动了，或者底图里本来就有个站着不动的人）；
   - 他的区域从不盖到任何一个留下来的人身上。留下来的人被认为在最初和最后一次找到他的地方前后各待 1 秒（认不出来不等于走了），攀爬者除外——计划说得出他去了哪。一个人因此留下，他就成了「留下来的人」，再反过来检查其余的人，直到不再变化。
3. 底图是计划给的那些时刻（`plate.times`，可以在这一趟之外）的画面逐像素取中位数；每张画面里 `keep` 框（放大一圈）以内的像素不参与，少于 3 张画面能作数的像素没有底图，那里的东西永远不会被换掉。只为候选的人经过的那一块做底图，画面先写到缓存再一条一条地算，不把几十张整幅画面同时放在内存里。
4. 没有人能消干净时，画面原样导出，不报错、不提示。被消掉的人所在的区域（边缘按计划的 `feather` 羽化）换成底图，`keep` 框以内始终是原画面。每个区域只属于一个被消掉的人，区域之间从不合并：同一时刻能消的人超过着色器能处理的 8 个时，多出来的人（被找到次数最少的先）整段留下，而不是把几个区域并成一个更大的。

所以：一直站着不动的人消不掉（他在底图里）；和攀爬者有过重叠的人、走到一半被挡住或认不出来的人、从留下来的人身前身后走过的人、灯光或机位变过的片子，都保持原样。没被消掉的人，整段片子里一个像素都不会被换。找人靠通用的检测模型，会漏认、会认错；漏认的人留在画面里，把别的东西认成人时换上去的是同一面墙。检测模型给的是框不是轮廓，换掉的是一个放大了一圈的矩形区域。找人这一步可以替换（`PeopleFinder`），设备测试用一个按颜色找方块的替身。

### 拍一趟

攀爬册的主按钮，产品说明与 iOS 同一份：[product-design.md 的「拍一趟」](../ios/product-design.md#拍一趟)。这里只写 Android 的落地。拍摄页面怎么判断不在这个仓库里，接口以已安装数据包里的约定为准。

- **入口**：攀爬册标题下的主按钮「拍一趟」，下面是次要的「导入」。
- **布局**：从上到下是顶栏（关闭、岩馆、难度）、关于岩馆的那一条提议（一行，可以点叉关掉）、机位提示（一行，指示条在它的右端）、画面、颜色与标记、录像按钮。机位提示在画面上方而不是压在画面上：结束点在墙的最上面，那里要看得见、点得到。录像中的那句「手机放稳，去爬吧」在画面下方。为了把地方留给画面：不显示状态栏，画面下方的几行字用小一号的字、引导最多两行，录像按钮也小一号。1080×2400 的屏幕上，平常状态画面占屏宽的 81%，认出线路、多出两行字时 73%；16:9 的小屏幕（720×1280）上各部分不重叠，但直立的 16:9 画面受高度限制只有屏宽的一半左右。拍摄界面是盖住整个界面的全屏对话框（深色底、竖屏——整个应用本来就锁定竖屏），打开期间它的窗口带 `FLAG_KEEP_SCREEN_ON`。
- **权限**：第一次打开时请求 `CAMERA`。拒绝后画面处是一张说明卡片，给「打开系统设置」和「改从相册导入」；从系统设置回来会再试一次。没有相机的设备只给后者。不申请 `RECORD_AUDIO`：录的片子只有画面轨。
- **画面来源是一个接口**（`CaptureSource`）：上直立的帧、预览视图、把画面写成片子。真机上是 `CameraSource`（CameraX：`Preview` + `ImageAnalysis` + `VideoCapture<Recorder>`，后置主摄，三路都取 16:9，画面和录下来的是同一个范围；录像取 1080p，不够就取相邻的档，码率用 CameraX 对这一档的默认值；`ImageAnalysis` 取 1280×720 附近的 YUV 帧）。调试构建和设备测试用 `FileCaptureSource`：循环播放一个视频文件，预览是文件自己的画面，「录像」是从下一个关键帧起把文件里的编码帧原样抄进一个新片子。之后的检查、保存、排队对两种来源是同一份代码。
- **交给拍摄页面的帧**（`CapturePipeline`）：取景时最快每 0.5 秒一帧；开始录像、发出 `lock` 之后不再给（页面会把它们全丢掉），也不再为它缩图和跑姿态识别；页面还没就绪、或者已经确定用不了时同样不准备；在处理器上用 `YuvConverter` 从 YUV 直接缩到短边 360（两边取偶数）并转正，JPEG 质量 70，base64。同时带上手机的姿态：重力传感器（没有就用低通后的加速度计）换成仰角和侧倾，陀螺仪换成两帧之间角速度的均方根；传感器都没有时只是不带。设备跟得上时还带一帧姿态识别的 33 个点（同一个打包的模型，CPU）；平均一帧超过 0.15 秒或者机身发热就停掉，这一趟不再跑。水平视场角按实际交给页面的那一路画面算：绑定之后取所绑相机的感光区域（像素阵列里的有效部分）和焦距，等第一帧到了，再按这一路画面自己的宽高比算出它在感光区域里占的范围（16:9 的画面取自 4:3 的感光区域时保留全长、裁掉高度），直立画面的宽对应其中的短边。这个值没有在真机上对着实际画面核对过。
- **拍摄页面**用和岩馆、分析页面同一个 `PackWebView`（同一个本地地址、只提供清单里的文件、同样的离线拦截和消息垫片），地址是 `capture.html?lang=<界面语言>`。它没有界面：`WebView` 以整屏大小放在拍摄界面的最底层、被深色底盖住，留在窗口里，所以不会被当成不可见页面而降速。原生调用都经 JSON 编码生成 JavaScript 字面量；`tap` 的返回值用 `evaluateJavascript` 的回调取。不支持在文档开始时注入脚本的旧 WebView（例如 Android 12 模拟器上的 91）上，消息垫片直接写进每个 HTML 文档、作为第一个脚本（见上面的[消息桥](#消息桥)）。消息宽松解析：不认识的类型、代码、字段忽略，缺的字段按保守的读法。页面 5 秒不回话，提示换成「机位检查暂时用不了，照常可以录。」，它再回话就恢复；画面本身停过（应用退到后台、相机被占用）之后重新来帧时，这 5 秒从头算，不会一回来就闪一下这句话。页面加载之后 15 秒还没说自己就绪，就不再等：提示同样换成这一句，不再为它准备画面（它之后要是就绪了，照常恢复）。
- **岩馆**：默认是最近**建立**的那条带岩馆的记录的那一家（按记录建立的时间，不按可以手改的攀爬时间），应用不会自己换。位置只用平台自带的 `LocationManager` 取一次，不用 Google Play 服务：`fused`、`network`、`gps` 里开着的各问一次，谁先答就用谁的（哪个先答因机型而异，室内卫星可能根本不答）；20 秒都没答就用系统上次知道的位置，再没有就是「暂时取不到位置」。`ACCESS_FINE_LOCATION` 和 `ACCESS_COARSE_LOCATION` 一起申请，点了「按距离找附近的岩馆」才出现系统的询问，Android 12 起系统让用户选精确还是大致，拒绝过就不再出现这一段。两种授权应用都能用：精确位置下显示距离，300 米内知道自己位置的岩馆会带着距离提出来；大致位置下系统给的位置有一两公里的出入，所以只排序、不显示数字，最近的一家只当成猜测（「可能在：某岩馆」）。排序规则与 iOS 相同：只有 `poi` / `address` / `station` 参与排序；只知道最近车站的写成「约」，取整到 0.5 公里，而且不小于 1 公里（车站离岩馆通常就有这么远）；区、市级的条目列在「同城的岩馆」里不带距离；300 米以内的提议只对 `poi` / `address`，而且只是提议。还没选岩馆时，画面上方那一条另有两种：允许过位置、目录里有排得上的岩馆时，把最近的一家当成猜测提出来（「可能在：某岩馆」，不带距离，旁边「选这家」和一个叉）——它或者只知道最近车站，或者手机只给了大致位置，说不了更多；从没问过位置时是一个「按距离找附近的岩馆」，点了才出现系统的询问。岩馆表里，「正在定位…」、「暂时取不到位置。」（带「再试一次」）、「没有位置权限。在系统设置里允许 BetaBuddy 使用位置，就能按距离找岩馆。」是三句不同的话；只有拿到了位置而附近确实没有目录里的岩馆，才写「附近没有找到目录里的岩馆。」。显示距离的那张表下面写着「© OpenStreetMap contributors」。
- **选的岩馆是不是数据包里的一家**：清单的 `venues[].directoryIds` 列了目录 id 就按 id 对，否则按名字对（品牌和分店两段都对上、而且只对上一家）。对上了才把岩馆 id 交给拍摄页面。换了岩馆，页面的这一次取景作废、下一帧起重新开始；在那之前按了录像，页面手里的判断还是上一家的，这一趟就不发 `lock`、不带计划地录，不会把上一家的计划存到新岩馆名下。
- **认出的线路**：写成「认出来像是：名字 · 难度」（名字取页面按界面语言给的，没有就取线路自己的名字，再没有就是 id；难度是页面给的原文），旁边是「不是这条」。认出来之后、用户还没标起步之前，引导那一行换成「起步和结束是按认出的这条线标的。不对的话，点一下岩点改。」。「不是这条」：页面有 `rejectRoute` 就告诉它，它会换成下一条对得上的线或者不再报；页面没有这个调用时它还会报同一条，应用这一趟不再显示它。没被否掉的那条随记录保存，只存 id 和线路自己的名字：页面按当时的界面语言给的名字和难度文字不进存档（摘要里的线路同样只留这两项）。被否掉的不保存。
- **难度**：用户还没选过难度、认出的线路的难度又正好写成 V0–V12 时，替用户填上，顶部的难度变成黄绿色，下面多一行「难度是按认出的线路填的，可以改。」；线路被否掉或者不再被认出，填上的难度跟着撤掉。用户自己选过之后不再改。别的写法的难度只显示、不填。
- **录像**：由来源自己写文件（CameraX 的 `Recorder` 写到 `filesDir/BetaBuddy/staging/`），不经过上面那条取帧的路。**`Recorder` 写不出画面时换成应用自己的编码器**：`Recorder` 把相机给每一帧打的时间当成系统的开机时间来用，相机的时间从别处数起时它一帧都不留（见验证记录里 Android 12 模拟器的那一条）。按下录像 3 秒它还没写进任何画面（或者它自己空着结束了），应用就不动声色地接手：把本来就在收的那一路画面（`ImageAnalysis` 的 YUV 帧，1280×720）用 `MediaCodec` 编成 H.264（码率按像素数算，限在 2–12 Mbps，720p 约 6 Mbps）、`MediaMuxer` 写成 MP4，时间用应用自己的单调时钟，画面的方向靠文件里的旋转标记（和手机相机应用的做法一样），所以片子是直立的 16:9、只有画面轨，姿态识别和分析页面照常收。切换不重新绑定相机，预览不闪，界面上什么都不变；切换之前的那 3 秒不在片子里。这台设备会记住（`SharedPreferences` 的 `capture` 里的 `ownRecorder`），下次打开相机就不再绑 `Recorder`，一按录像就用自己的编码器。每段片子是谁写的记在日志里（`clip written by the camera library's recorder` / `by the app's own recorder`），调试读数里也有。自己的编码器也写不出来时，才提示「录像没能开始，请再试一次。」。没有走「第二个 `Preview` 接编码器的输入面」那条路：那要在录像中途重新绑定相机（预览会断一下），而且三路输出在 LIMITED 级的相机上没有保证；用已经在收的那一路不需要动相机，哪一级的相机都一样。上限和 iOS 一样是 20 分钟（差 2 秒），自动停下时写的是「录到 20 分钟，自动停了。」。导入限 3 分钟、500 MB；相机自己录下的记录在姿态识别时按 20 分钟、不限大小来收。分析页面拿到的是全片均匀取的约 60 帧和全部姿态，两个平台相同。开始前可用空间不足 600 MB 不开始；录像中每 3 秒看一次，低于 250 MB 或机身过热（`THERMAL_STATUS_CRITICAL`）就停下并保存。应用退到后台、相机被别的应用占用时同样停下并保存已经录到的部分。不到 1 秒的不保存。取景时画面停了（相机被别的应用占用、出错、应用在后台）超过 3 秒，预览就是一张定住的画面，录像按钮不能点，画面重新来了才恢复。开始 6 秒后两条路都还一帧没写进去就停下并提示「录像没能开始，请再试一次。」，不让人对着一个什么都没录的相机去爬。
- **先保存，再分析**：停止后一次写入完成——原片改名进 `filesDir/BetaBuddy/`、缩略图、拍摄计划（`<记录 id>.capture.json`，原样保存）、存档里的岩馆、难度、颜色、摘要、姿态识别的请求和「识别完接着分析」的请求。写完才显示「已保存到攀爬册」。保存失败时片子留着，可以「再存一次」或「放弃这段录像」；在用户选其中一个之前，关闭和系统返回都不起作用，片子不会被悄悄删掉。界面被系统收走（或者应用被关掉）时，没存进去的片子留在 `staging/` 里，旁边有一个开始录像时写下的小文件（岩馆、难度、开始时间）。下次启动时清理 `staging/`：相机录下、能播放、不短于 1 秒的片子连同那个小文件里的信息补进攀爬册（没有计划，照常排姿态识别）；录到一半进程就没了、文件没有收尾所以放不了的，和没导完的导入一样删掉。
- **相机开着时什么都不分析**：进程里有一个开关（`CameraGate`）。它开着时姿态识别服务不启动，正在跑的那一条被停下、请求留在存档里；它关上（存好了、或者离开拍摄界面）之后服务重新启动。
- **识别完接着分析**（`AnalysisQueue`）：首页一直挂着一个队列。记录带着「接着分析」的请求、姿态识别已经做完而且有 world landmarks、数据包有分析页面时，它在首页最底层（整屏大小、看不见）打开分析页面，和用户自己打开时一样交画面、姿态，另外把拍摄计划经 `begin(meta.capture)` 交回去，结果照常保存。一次一条；相机开着或应用不在前台时不跑。姿态识别没找到人、数据包没有分析页面、十分钟没有结果时，请求撤掉，记录自己的「分析这一趟」还在。卡片上依次是「先存好了…」、「姿态识别好了，正在分析这一趟…」、「看分析」。同一条记录不会同时分析两遍：用户自己打开了这条记录的分析页面，队列就停下它自己的那一遍、撤掉请求，由用户打开的这一页来做；分析页面开着的记录队列不碰。分析页面在结果里说了它有没有用上拍摄计划时（新一些的数据包），这句话原样记在记录的 `capture.planUse` 里（`used`、`reason`、`start`、`finish`，字段名和 iOS 相同，两边的存档可以对照；数据包 1.9.3 起页面还可能给一个 `shift`——`dx`、`dy`、`rot`、`scale`，机位挪了多少——一起存，应用自己不读它）。没用上时，队列做完之后卡片上写的是「分析好了。取景时标的岩点和起步、结束点这次没有用上：机位和取景时对不上。」，不会说成用上了。
- **列表和回看**：用相机拍的记录在难度旁多一个色块（当时选的颜色，没有名字）。
- **调试启动参数**（只在 Debug 包里读）：`openCapture`、`debugCaptureVideo`、`debugCaptureFov`、`debugCaptureAttitude`、`debugLocation`、`debugCaptureOverlay`（在画面左下角画出交给页面的视场角、仰角、侧倾、晃动、页面每秒回话数、交接耗时和当前的问题代码）、`debugCaptureKeepFrame`（把最近交给页面的那一帧另存一份，拿出来看方向对不对），见 `MainActivity`。这些读数不是给用户看的字，不进字符串资源，Release 包里没有。

### 文件夹与组合筛选

与 iOS 的[收纳交互](../ios/product-design.md#收好每一趟)一致：文件夹可以新建、改名、删除，删除后保留视频并移回未分类；每条记录最多属于一个文件夹。导入时优先读取所选媒体的 `DATE_TAKEN`，其次读取视频容器的拍摄时间（含时区）；缺失或无效时使用当前时间并提示。日期与时分直接展示并允许修改，回看时也能通过「整理」修改时间、岩馆与归属文件夹。

首页使用横向文件夹入口和紧凑筛选入口，岩馆、难度、时间与原有完攀状态、搜索共同生效。日期以用户本地日历计算，旧记录继续用原日期。全国岩馆目录从 assets 中离线读取，可按城市和馆名搜索，未收录时手填；导入和整理时选岩馆不用位置，按距离排序只在拍摄界面、用户点了才问。目录来源与覆盖见[目录说明](../gym-directory.md)。

存档新增字段兼容旧版索引，缺少目录关联或文件夹的记录仍能读取；分类操作只更新 JSON，不搬动原片、不重新分析。

## 隐私与存储

- **权限。** Manifest 声明本地分析服务用的 `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_DATA_SYNC`、`FOREGROUND_SERVICE_MEDIA_PROCESSING`，可选的 `POST_NOTIFICATIONS`，以及应用内相机用的 `CAMERA` 和按距离给岩馆排序用的 `ACCESS_COARSE_LOCATION`、`ACCESS_FINE_LOCATION`（都是用到时才问，两条位置权限一起问、由用户选给哪一种，拒绝后其余功能照常）。不申请麦克风、相册、存储或网络权限，并移除依赖库会合并进来的 `INTERNET`、`ACCESS_NETWORK_STATE` 和 `WAKE_LOCK`。CameraX 合并进来的只有一个不导出、默认停用的 `MetadataHolderService`（它用来找到相机实现），没有权限。另有 AndroidX Core 自动加的一条应用自用的签名级权限。AppCompat 带来的 EmojiCompat 启动项也已移除（它会向系统字体服务要新的表情字体）。
- 岩馆只在本机记两个布尔值（是否读过说明、手势提示是否看过），存在应用私有的 `SharedPreferences` 里。攀爬册的数据在 `filesDir/BetaBuddy/`（索引、原片、缩略图、分析结果文件、剪辑计划、应用内拍摄的记录的拍摄计划；结果和计划里各有一张由画面合成的墙面图），另有 `SharedPreferences` 里分析页面上一次用的身材参数，以及相机的两项设备记录（这台设备要不要用应用自己的编码器、用户是否拒绝过位置）。都不写外部存储。给分析页面和拍摄页面的画面只在内存里。位置只取一次、只用来排序，不保存。
- **不进备份，也不随换机迁移。** `allowBackup="false"`、`fullBackupContent="false"`；`data_extraction_rules.xml` 把 `<cloud-backup>` 和 `<device-transfer>` 两节的全部数据域都排除（Android 12 起两者分开，`allowBackup` 管不到设备间直传）。
- **第三方许可全文**随应用打包在 `assets/licenses/`（组件清单、Apache License 2.0、MediaPipe 原生库的全部声明），在「设置与关于」→「开源许可」里离线查看；许可保持英文原文。
- 「设置与关于」里的「帮助与支持」和邮箱会交给系统的浏览器 / 邮件应用打开；分享复盘文字走系统分享面板，只有文字。自动剪辑出来的片子只在应用缓存里（`cacheDir/edits/`，做底图时的临时画面在 `cacheDir/edit-work/`，用完就删）；用户点「分享视频」时，这一个文件经应用自己的 `FileProvider` 交给系统分享面板——这是视频离开应用的唯一途径，由用户自己发起。应用自己不联网。

## 与 iOS 的差异

| 方面 | iOS | Android |
| --- | --- | --- |
| 页面地址 | 自定义协议 `gympack://local/` | 保留域名 `https://appassets.androidplatform.net/gympack/` |
| 提供的文件 | 包目录里存在的文件 | 只有清单列出的文件 |
| 断网手段 | 内容规则 + 导航限制 | 无联网权限 + `blockNetworkLoads` + 请求拦截 + 导航限制 |
| SDK 的使用统计 | 上报工厂换成空实现 | 无联网权限，并移除上报后端的发现服务 |
| 消息桥 | `WKScriptMessageHandler` | `addJavascriptInterface` + 文档开始时注入的垫片 |
| 分析页面 | 全屏页面，右上角「完成」 | 全屏对话框，顶部原生窄栏里的「完成」，系统返回同效 |
| 自动剪辑的渲染 | AVFoundation | Media3 Transformer + 自己的 OpenGL 着色器 |
| 自动剪辑里找人 | 系统的 Vision | 随应用打包的 EfficientDet-Lite2（MediaPipe `ObjectDetector`），给出的是框，不是轮廓 |
| 安全区 | 页面用 `env()` 自己留白 | 原生侧留白，页面拿到的 inset 为 0 |
| 语言 | 跟随系统，或在应用内选，不重启 | 同左，Activity 以新语言重建；Android 13+ 与系统的「应用语言」同步 |
| 设置与关于 | 从底部弹出的一页；显示已保存的攀爬数量、在线隐私政策链接 | 导航栈里的一页，系统返回退出；不显示数量，隐私政策只有内置的一份；多一项「开源许可」 |
| 备份 | 排除云备份 | 排除云备份和设备间迁移 |
| 视频来源 | 相册或文件 | 系统照片选择器 |
| 调试参数 | 启动参数 `-gymQuery` 等 | intent extra，另有 `gymNoticeSeen` |
| 应用内相机 | AVFoundation，帧同时给检查和写片子 | CameraX，录像由 `Recorder` 自己写，检查另取一路小帧；`Recorder` 写不出画面时由应用自己的编码器接手 |
| 位置 | 使用期间，可精确可大致 | 两条位置权限一起申请，Android 12 起由用户选精确或大致；只用平台自带的定位 |
| 岩馆选择表 | 半屏的表，可进全部岩馆 | 对话框，可进原有的岩馆选择对话框 |


## 相册与人物选择开发分支

相册自动收录与多人选择仍在开发，不能视为现有正式版功能。多人候选提取和与 iOS 共用的本地策略已通过基础集成检查；候选带原视频坐标、姿态和粗粒度衣着色样，没有人脸识别或跨视频身份。策略执行的 WebView 不开放网络、文件访问或原生消息桥，结束及取消后销毁。已接入轻量圈线点选、按时刻纠正、自动选择、保存与取消；候选按记录压缩存储，改选递增修订号并使旧结果失效，迟到的姿态及网页结果不能覆盖。常规后台姿态分析在私有策略可用时收集多个候选并自动选择。已选位置与姿态分别送入分析，缺姿态时不捏造动作。手动拖框的局部识别与独立位置追踪尚未移植；真实遮挡和交叉未验收。相册分类、权限和自动导入也仍待实现。完整范围和验证记录见 [相册归集与人物选择](../ios/camera-library-selection.md)。
